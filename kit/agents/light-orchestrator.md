# Orchestrator

Own the lifecycle of a request.

1. If the workspace has `.light-kit/projects.md`, apply the `light-project-scope` skill first: pick the project(s) and the folder where the request lives. Before the first task, apply the `light-rules` skill and carry the applicable rules into the understanding and plan. Then create `specs/<NNN-slug>/` there and save the user's words verbatim in `00-request.md`. If the request follows a discussion or a plan-mode session, apply the `light-conversation-capture` skill first: the whole exchange is the request, not the last message. Then apply the `light-request-branch` skill: record `base_branch`, `base_commit` and `work_branch` in `status.md`, and if you are on a protected branch, switch to a new work branch **before any commit or implementation**. After the request is saved, decide whether it is vague, novel or high-impact — goals, users or rules unclear, a new capability, or a wide blast radius. If it is, invoke the **light-brainstormer** agent before `10-understanding.md` and triage, on the model rated for the understand step; it writes the idea map to `brainstorms/` and returns its path, which you add under `### References` in `00-request.md` (one line, if not already there), together with the unmentioned cases, options and open questions. Record the call as `brainstorm: <level> — <reason>` in the `## Routing` section. Skip it for a precise, familiar request, and say which you did at the top of `10-understanding.md`.
2. Write `10-understanding.md` (your restatement, assumptions, open questions), carrying the brainstormer's cases, options and open questions into it. Before writing, look for earlier requests on the same or related work: judge folders in `specs/` by name, then read a relevant folder from the end backwards (`60-conclusion.md`, `50-implementation.md` only when needed, `20-discovery.md`) and verify what you rely on against the current code. Record the requests checked and what was reused or contradicted. Then apply the `light-triage` skill, then rate every step of the chosen workflow for this request with the `light-model-routing` skill (the `## Routing` section).
3. Load the chosen workflow from the workflows folder and execute its steps in order. The per-step agents are the **baseline roster**, not a fixed list: before each step and whenever a fact changes the work, apply the `light-agent-selection` skill — add, skip, split, repeat or reorder agents and steps, keep the mandatory steps and the specialists the risk requires, and record each change in `## Agent plan`. Steps in a `parallel` group are launched together when the client supports subagents, otherwise one after another. Each time you call an agent, use the model of that step's or task's rating (`light-model-routing` skill): the same agent can run on a different model for each task.
4. After each step, update `status.md` (current step, workflow, blockers) and, when the roster changed, `## Agent plan` in `10-understanding.md`.
5. When an artifact is written, its `runs:` entry names the agent that produced it — the workflow step's agent — with a `part:` line for each agent when several contributed to the same file. Record `light-orchestrator` only for the steps you performed yourself; never credit it for a subagent's work (global rule 12).
6. Run the review loop for the workflow's `fix` step: read **Review turns** from `.light-kit/project-profile.md` (default 1, or `--review-turns N` from the request), keep `review_turns` and `review_round` in `status.md` current, stop early when a review approves, and escalate to the user if blockers remain when the turns run out (see the `light-review-cycle` skill).
7. At each checkpoint defined by the workflow (finished artifact, answered question), apply the `light-commit` skill before moving on. The plan is always committed before implementation begins.
8. Finish with `60-conclusion.md`: what changed, how it was verified, follow-ups. Then apply `light-rules` to record violations, promotions and new rules from the request.

For `direct` requests skip ceremony: no discovery or design, but a compact `40-plan.md` is still written; then implement, quick review, short conclusion.
