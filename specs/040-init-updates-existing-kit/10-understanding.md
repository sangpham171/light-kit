# Understanding

## Restatement
Running `light-init` in a project that already has `.light-kit/` must bring that folder's documents up to the current kit: new sections, settings and keys are added; nothing that is already there is changed or deleted.

## Prior requests
- **037 (project rules):** `.light-kit/rules.md` is seeded per project and is user-owned; confirmed by the current code. Reused: the file is merged, never replaced.
- **039 (promotion threshold):** added `## Rules` / `Promotion threshold: 3` to the profile template. Its conclusion records TD-1: existing profiles and rules files keep the old wording after an upgrade because installs never overwrite user files. This request resolves it.
- **000–039 scan:** no earlier request implements an in-place update of `.light-kit/`; `light-plan`, `light-standardize` and `light-audit` cover other refresh paths.

## Assumptions
- "Documents in this folder" means the kit's own documents in `.light-kit/`: the kit copies under `templates/` and the project-owned files seeded from them (`project-profile.md`, `rules.md`, `hooks.config.json`, `models.json`, `projects.md`). User artifacts (`specs/`, `brainstorms/`) are out of scope.
- The new kit content reaches an installed project through the installer, which puts it in `.light-kit/templates/`. `light-init` merges from those copies and cannot fetch a kit version by itself.
- "Update, don't erase" means additive: existing lines and JSON values win. Replacing kit prose in a section the user may have edited is not attempted.
- The codebase map, assessment and standardization backlog are generated by `light-init`; an update run fills them only when missing, so applied backlog state is not lost.

## Open questions (with proposed defaults)
- Should changed kit prose inside an existing section be replaced? Proposed default: no; only missing whole sections and missing `key: value` settings are added. A three-way merge would need stored baselines, more risk and more state.
- Should `.light-kit/hooks.config.json` also gain new hook mode keys? Proposed default: yes, missing modes are added with their built-in default (absent already means that default), existing values kept.
- First run on an install created before this change: the templates are stale. Proposed default: the installer refreshes templates on the next upgrade; until then the merge adds nothing new.

## Requirements
1. `light-init` detects an existing `.light-kit/` and updates it in place instead of re-creating documents.
2. The update adds missing `##` sections and missing `key: value` setting lines to the project profile, rules and projects registry, and missing keys to the hooks config and models table.
3. No existing line, value or rule is modified or deleted.
4. The kit copies under `.light-kit/templates/` are refreshed on reinstall; user-owned seeds stay.
5. The update is idempotent and reports what it added.
6. The behaviour is documented in the skill, `docs/usage.md` and `docs/installation.md` where needed.

## Acceptance criteria
1. In a temp install, customized `project-profile.md`, `rules.md`, `hooks.config.json` and `models.json` keep every pre-existing line/value after an update run, while a new template section, setting and key appear.
2. A second update run writes nothing.
3. Reinstall refreshes `.light-kit/templates/*` and keeps `.light-kit/rules.md` and `.light-kit/project-profile.md`.
4. The generated `light-init` skill and the docs describe the update path.
5. `npm test` and `node --test tests/kit.test.mjs` pass.

## In scope / Out of scope
- In: an installed `merge` script, its generation, the `light-init` update branch, template refresh, tests and docs.
- Out: three-way/diff3 merge or stored baselines; rewriting kit prose in filled sections; changing `specs/`, `brainstorms/`, `usage.json`; any network or model call.
